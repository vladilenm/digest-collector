# Подключение отправщика

## 1. Источник и журнал

Источник должен предоставлять `digest.newsletter_issue_source_v1` с `issue_id`, `topic_id`, `from_date`, `to_date`, `prepared_at`, `schema_version`, `document` (NewsletterIssue email-period v1). Фильтр темы обязателен: `DIGEST_TOPIC_ID=ai` для AI-дайджеста. Сам сервис не создаёт и не меняет схему источника.

Создать две отдельные login-роли без прав владельца. От владельца источника выполнить:

```sh
psql "$DIGEST_OWNER_URL" -v ON_ERROR_STOP=1 -v reader_role=digest_mail_reader -f database/reader-grants.sql
```

Отдельное окружение мигратора получает `NEWSLETTER_MIGRATION_URL` и политику подключения журнала. Выполнить:

```sh
npm run migrate
psql "$NEWSLETTER_MIGRATION_URL" -v ON_ERROR_STOP=1 -v runtime_role=digest_mail_journal -f database/unisender-grants.sql
```

Файл `003-unisender-campaigns.sql` сохраняет номер исходной миграции для совместимости существующего журнала. Старые таблицы NotiSend не создаются. Мигратор берёт блокировку, применяет SQL транзакционно и отмечает файл в `newsletter.schema_migrations`; повторный запуск ничего не меняет. Runtime получает только `NEWSLETTER_DATABASE_URL` роли журнала и `DIGEST_DATABASE_URL` reader-роли. Удалить credential мигратора из постоянно работающего приложения.

По умолчанию TLS проверяет сертификат. Для сервера без TLS в доверенной приватной IPv4-сети явно задать соответствующие `*_DATABASE_NETWORK=private` и `*_DATABASE_SSL=off`. Без TLS допускаются только RFC1918-адреса, а для локальных тестов — `network=local` и разрешённые loopback/Compose-имена. Параметры URL не могут переопределить проверенную политику подключения.

## 2. Unisender

- Существующий API-ключ передать через `UNISENDER_API_KEY` только этому сервису.
- Выбрать отдельный список в `UNISENDER_LIST_ID`; форма лендинга должна подписывать в этот же список.
- Подтвердить отправителя `UNISENDER_FROM_EMAIL` и почтовые DNS; включить double opt-in и единственное приветствие в кабинете.
- До теста держать `UNISENDER_CAMPAIGNS_ENABLED=false`, `UNISENDER_ACCOUNT_READY=false`, `UNISENDER_PUBLIC_DELIVERY_ENABLED=false`.
- Стандартная статистика открытий и переходов Unisender включена по выбору владельца. GA/Яндекс.Метрика выключена; фактические настройки проверять в деталях кампании и доставленном письме.

## 3. Timeweb App Platform

После согласования ресурса создать **отдельное** backend-приложение из `vladilenm/digest-collector`, ветка `main`, Node.js 24, фреймворк «Другой». Размещать в московской приватной сети источника. Сайт Club Landing остаётся на прежнем месте.

| Поле | Значение |
| --- | --- |
| Команда сборки | `npm ci --omit=dev` |
| Команда запуска | `npm start` |
| HTTP-проверка состояния | пустое поле |
| Домен | не требуется |

Пустой HTTP healthcheck проверяет запуск контейнера. Отдельно проверить, что процесс продолжает работать, получает материалы и записывает результаты в журнал. `disabled`, `invalid_config` или завершившийся процесс не считать успешным запуском. Переменные формы подписки, Next.js и секреты сайта сюда не передаются.

Можно развернуть через приложенный Dockerfile вместо Node.js-сборки; не запускать оба варианта одновременно. Docker-контейнер принимает те же env-переменные.

## 4. Проверка и включение

1. Выбрать начальную дату `UNISENDER_FIRST_SEND_DATE`. Dry run использует то же расписание: до 10:00 МСК или вне выбранного дня вернёт `not_due`.
2. Выполнить `npm run dry-run`: ожидать `preview` с числом материалов; API-ключ и роль журнала для этого не нужны. `skipped` означает отсутствие материалов, `failed` — ошибку чтения или формата.
3. В тестовом режиме включить `UNISENDER_CAMPAIGNS_ENABLED` и `UNISENDER_ACCOUNT_READY`, оставить `NEWSLETTER_TEST_RECIPIENT=digest@irreplaceable-ai.ru`, публичный флаг выключенным. Выполнить `npm run once`.
4. Проверить фактическую доставку письма, ссылки, SPF/DKIM/DMARC, персональную отписку и исключение отписавшегося контакта. Принятия API недостаточно.
5. По готовности очистить тестовый адрес, включить публичный флаг и запустить постоянный процесс. Журнал разделяет test/public; публичная кампания может уйти в тот же день после успешного теста.

## Остановка и сбои

Чтобы остановить отправку, выключить приложение или `UNISENDER_CAMPAIGNS_ENABLED` и перезапустить процесс. Журнал сохранить. Не удалять запись ради повторной отправки: при `sending`, `preparing`, `uncertain` сначала сверить ID и фактическую кампанию в кабинете. Автоматического replay, переноса расписания и повтора неопределённых запросов нет.

Логи содержат только категорию результата и количество материалов. Секреты и полный ответ API не печатать. Настройки и история подписчиков остаются в Unisender.

## Готовый выпуск за период

Отправщик читает **один** email-period v1 за точные fromDate–toDate из `digest.newsletter_issue_source_v1`. Topic Digest выполняет редактуру всего периода и сохраняет максимум 8 карточек. Коллектор проверяет контракт, тему и даты, верстает карточки с фото/видеопревью и ссылками на сайты. Telegram URL запрещены контрактом. Все медиа повторно проверяются перед отправкой; одна недоступная картинка не удаляет остальные карточки. Редиректы при этой повторной проверке не разрешены.

`awaiting_issue` означает, что готового выпуска пока нет: worker ждёт следующего тика, журнал не захватывается и Unisender не вызывается. `empty` — готовое редакционное решение без карточек, оно записывается как `skipped`. Ошибки контракта никогда не включают fallback к дневным новостям. Отправленные ранее кампании сохраняют прежние ключи и не повторяются после обновления.

Согласовать `NEWSLETTER_FIRST_SEND_DATE` producer с `UNISENDER_FIRST_SEND_DATE` по трёхдневному циклу. Producer начинает в 09:00 МСК, sender сохраняет свой порог 10:00. Reader получает только SELECT нового view; прежнее разрешение на дневной view можно отозвать после переключения. Runtime не получает owner credential.
